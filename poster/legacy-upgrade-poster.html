AI-Driven Automated Upgrade of Legacy Systems

Can an agentic LLM pipeline modernise an outdated codebase without breaking it? Evidence from ten end-to-end runs

Dhruv Erinjery, Jinhao Zhang · Supervisors: Jing Sun, Mengze Li

Department of Electrical, Computer and Software Engineering, The University of Auckland, New Zealand · in partnership with Digital Services, University of Auckland Library

PART IV PROJECT 2026
Legacy Upgrade System
Codex $upgrade pipeline · GPT-5.5 · GitNexus
Introduction
Research question: can a multi-agent LLM pipeline analyse, plan, refactor and validate an upgrade of a legacy system so that the result builds, keeps its original behaviour, and costs less than a manual upgrade?

Background

  • Legacy software is long-lived, poorly documented, costly to maintain and exposed to security risk. Manual modernisation needs scarce specialists and takes months, by which time requirements have moved on [1, 2].
  • LLMs generate, refactor and document code well, but hallucinate, plan poorly over multi-step tasks and lose context on large repositories with long dependency chains [3, 6, 10].
  • Prior work covers isolated pieces: architecture recovery (MDRE-LLM, SARIF) [4, 5], code-form planning (CodePlan) [6], agent memory (Mem0, SimpleMem) [7, 8], documentation agents (DocAgent) [9]. No end-to-end framework joins analysis, planning, transformation and validation.
  • Human validation is still essential: analysts who over-trust LLM output introduce automation bias [3, 11].

Objectives

  1. Build an intelligent upgrade framework: analyse → plan → generate tests → transform → validate, with human approval gates.
  2. Measure whether the upgraded system builds, passes its checks and preserves behaviour.
  3. Measure tokens, cost and wall time per upgrade.
  4. Compare with dependency tools already in use (Dependabot, Renovate, Codemod).

Upgrade Pipeline

One orchestrator agent runs six specialised stages in strict order through the OpenAI Codex CLI. Each stage writes its full artefact to disk and hands the next stage a compact summary, keeping every context window small. GATE marks where a human must approve before the pipeline continues.

O
Orchestrator ($upgrade skill)
Asks for the current and target environment, build commands and URLs; preflights the repo and the GitNexus index; sequences the stages.
1
Analysis GATE
GitNexus dependency graph, impact queries and line ranges → affected files, risks, breaking-change notes.
2
Planning GATE
Line-aware change-plan.json: ordered changes, executor checks, key pages, user flows, scope-expansion budget.
3
Test generation
Small smoke and integration tests for the affected files, recorded in the plan.
4
Execution
Applies the plan on an upgrade/<slug> branch, runs every check, up to 3 repair rounds, commits once.
5
Validation and repair
Diff-to-plan alignment, builds, tests, Playwright key-page and flow checks; weighted confidence score, rejected below 0.80.
6
Browser console check
User reports console errors from the running app; in-scope errors repaired in up to 3 rounds and amended into the commit.

Evaluation Method

Ten runs, 19 June to 14 September 2026: nine on tv-radio with widening scope (frontend only → all packages → plus Solr → plus vendored client libraries → explicit breaking-pattern sweeps), one on codemirror5. Where the pipeline's verdict and independent verification disagree, both are reported.

Independent verification (18 Sep 2026)

  • Every upgrade commit checked out, npm installed and booted; node --check on all changed files; git grep for known breaking patterns.
  • Thirteen reference behaviours for tv-radio (module load, routes, search page, client bundle, admin search, CLI ingest, logging, Socket.IO auth) scored preserved or missing per run.
  • Tokens read from every Codex session log, sub-agent threads included; cost at GPT-5.5 list prices (US$5 / M uncached input, $0.50 / M cached, $30 / M output).

Next Steps
  • Never approve without runtime evidence: boot every entry process the plan touches, and make "no startup evidence" a hard reject.
  • Apply the known-break checklist to every major-version jump during analysis, and flag callers of an upgraded package that the plan did not touch.
  • Replace generated tests with boot-and-probe tests per entry point and a CLI run per user command; schema-check change-plan.json before execution.
  • Run a controlled ablation: one tool version, two tasks, four configurations, three repetitions, one oracle script independent of the pipeline.

What the runs show

  • Approval is not correctness. All three approved runs shipped a frontend that cannot serve pages; two rejections were about agent files in the diff, not code.
  • Bumping works, behavioural migration does not. Five signature-preserving breaks recurred every run: Express 5 route syntax and query objects, uglify-js 3 input, async 3 queue callbacks, winston 3 with legacy logstash, influx 5. Only when the user listed them in the prompt (R9) were they planned and fixed.
  • Generated tests gave no signal. Nine runs, zero real detections: they asserted version strings, require() and mocks, never a live route or CLI run.
  • The validator improved late. Playwright and key-page checks caught real regressions in R8 and R9; earlier verdicts rested on diff hygiene.
  • True cost is 3 to 8× the orchestrator's status line. Median 10.6 M input tokens per run (93 % cached); the execution sub-agent alone used up to 13 M in one rerun.
  • Every run needed 1 to 4 human decisions beyond the two designed gates, and three runs needed a manual repair session afterwards.
