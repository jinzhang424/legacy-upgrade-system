# Evaluation C5: direct Claude Code session, monarch-legacy, Node.js dependency modernization for Node 18/20 LTS (25 Sep–3 Oct 2026)

**Verdict: the infrastructure-level upgrade is real and, by the session's own in-session tests, working — but the validation bar the user set was only partly cleared, and nothing has been committed.** The user asked an interactive Claude Code agent (Sonnet 5, no orchestrator, no sub-agents, no generated tests) to modernize `projects/monarch-legacy` (npm package `monarch-app@3.0.0`, a Hapi/Node backend serving a jQuery + Vue 2 hybrid frontend bundled with webpack, against GOLR/OWLSim/SciGraph services) for Node 18/20: swap `hapi`→`@hapi/hapi`, `inert`→`@hapi/inert`, Babel 6→7, webpack→5, webpack-dev-server→5, `node-sass`→`sass`, `eslint`→8, `vue`→2.7, `bootstrap`→5, `request`→`axios`, `moment`→`dayjs`, `gulp`→4, and bump `mocha`/`mustache`/`underscore`/`xml2js`, then verify with `npm install && npm run wbs-build && npm run start`, `npm run wbs-lint`, `make test`, `npm run dev` plus a live proxy check, five named browser workflows, `npm audit`, and a repeat under `USE_SPA=1`. A second, independent regression sits behind the first: with that error bypassed, the build instead renders `<img src="[object Module]">` for the two inline logo images, because `file-loader`/`url-loader`'s newer versions default to ESM exports and the template's plain `require()` no longer gets a string URL back. Neither regression was fixed — consistent with how every other defect found during verification in this series is treated, a found-but-unpatched break counts against the run, not as something the evaluator repairs on the run's behalf. ## Pre-existing baseline defects (confirmed, not attributable to this upgrade)

A later correction from the user, which this revision incorporates, confirmed the following as pre-existing in the repository *before* this session's upgrade work began — none of them are regressions this upgrade introduced, and several directly change how two of the findings below should be attributed:

- **Build-order defect.** `npm run wbs-build` only ever ran webpack; `conf/golr-conf.json` is generated by the separate Gulp build (`gulp make-golr-conf`). A genuinely clean checkout running `wbs-build` then `start` could fail with `ENOENT` on that file. This structure already existed at base commit `e337d87a`. This session never hit it, because `conf/golr-conf.json` already existed on disk from an earlier build; the session did not generate it freshly and so could not have surfaced this gap either way.
- **Retired backend services.** `conf/server_config_dev.json` points at `scigraph-ontology-dev.monarchinitiative.org`, `scigraph-data-dev.monarchinitiative.org`, `solr-dev.monarchinitiative.org`, and a legacy beta OwlSim endpoint — services that no longer provide the APIs Monarch expects, independent of any sandbox network restriction. This means several of this session's own "could not verify" findings (see 1.1 and 1.3 below) were **never passable by any upgrade**, not merely blocked by this particular environment. The session's own framing — "this sandbox has no outbound network" — was true but incomplete; the more precise cause is that the dev-tier backends themselves are gone.
- **Existing tests already depended on those retired services.** `apitest.js` could not complete its GOLR/SciGraph assertions and `class-info-test.js` failed resolving the SciGraph hostname *before* this upgrade, for the same reason this session's own run of `class-info-test.js` failed. `phenopacket-test.js`, which has no network dependency, remained runnable and passing pre-upgrade — this session never ran it, which is a real gap in its own verification (see "Run-specific recommendations"), independent of the backend question.
- **Windows script incompatibility and the Gulp `mkdir` task** were both pre-existing: many npm/Makefile commands use POSIX-only syntax (inline env vars, `rm`, background `&`, `ln -s`, colon-separated `NODE_PATH`) that does not run through `cmd.exe` directly, and Gulp's temporary-directory task's shell `mkdir` was never portable to Windows either. Both predate this upgrade and are not things the gulp 3→4 migration (or anything else in this session) broke.
- **Missing lint configuration** (`wbs.eslintrc` absent) was pre-existing, as the session itself suspected but could not confirm at the time.
- **Node 18/20 incompatibility was inherent in the old dependency graph** — `node-fibers`/`wait.for`, `node-sass`, the old Hapi, and the old Webpack/Babel/Gulp toolchain all targeted Node 6-era tooling and could not be expected to install cleanly on Node 18/20 without exactly the kind of intervention this session performed.
- **The old dependency graph's security debt, including the Axios 0.18 CVEs this upgrade specifically targeted, was pre-existing** — consistent with what `npm audit` showed in-session.
- **Two items remain baseline-indeterminate, not attributable either way:** the exact behaviour by which an unhandled Axios/`sync-rpc` rejection terminates the whole Node process (observed in this session's `class-info-test.js` run — see 1.2), and analytics-page behaviour (never investigated in this session at all). Neither has a successful pre-upgrade baseline to compare against, so neither is scored below as preserved, missing, or upgrade-caused.

This correction **does not change the strict C/T/FBSR scoring** in 1.1 below — those checks still did not run to a pass, regardless of why — but it does change which failures are fairly attributable to this session's work versus inherited, pre-existing baseline limitations that no upgrade session, in this sandbox or any other, could have cleared. It also reclassifies two cells in the 1.3 behaviour-preservation table from "missing" (implying the upgrade broke something) to "excluded" (the behaviour was already broken and nothing here regressed it).

## Run-specific recommendations

- **Commit before reporting a task as "done, verified as far as this sandbox allows."** Eight days of a clean, correct, uncommitted diff is still zero durability; a single `git commit` at the end of the upgrade work would have cost one tool call and removed the risk entirely, the same recommendation C4 made for PeelAndSlice.
- **State "not attempted" and "attempted but failed" in visibly different language, in the first sentence, not only in a detailed table several paragraphs down.** Three of the five incomplete declared checks in this run were never run at all (lint, the browser workflows, the `USE_SPA=1` dev-server half); the other two (the test suite, the `USE_SPA=1` build) were run and found broken. Those are materially different and differently serious gaps, and the closing summary's structure made them easy to conflate at a skim.
- **Follow the project's own CLAUDE.md impact-analysis mandate for every touched symbol, not a representative one.** Running `gitnexus_impact` once (on `wrapRouteGet`) and treating that as covering `wrapResponse`, `wrapRoutePost`, `wrappedHandler` and five other touched symbols is a reasonable judgement call under time pressure, but it is not what the project's own stated policy, which the harness surfaces unconditionally, actually requires.
- **Re-run the developer test suite against a reachable backend (or a local mock) before closing out a migration this size.** `tests/*.js` never got past the first network call in this sandbox; that leaves the actual behavioural correctness of the engine's GOLR/SciGraph-dependent methods — the part of the stack the fibers rewrite touched most directly — entirely unverified by anything other than code reading.
- **Treat an evaluation harness's own setup step (here, `gitnexus analyze`) as part of the diff-hygiene surface to report, not as neutral background.** It produced four new untracked paths and a `.gitignore` edit that had nothing to do with the upgrade and were never surfaced to the user.
- **For a target this size, check whether the named backends are even still live before the session starts, not just whether this particular sandbox can reach them.** The brief named five browser workflows and a test suite that all depend on `monarchinitiative.org` dev-tier services; those services are confirmed retired, independent of sandbox network access. A one-line reachability check at the start — ideally against a source of truth that distinguishes "retired" from "temporarily unreachable" — would have let the session say so immediately and precisely, rather than attributing the gap to its own sandbox after most of the upgrade work was already done.
- **Run every test that doesn't need the network, even when most of the suite does.** `phenopacket-test.js` had no dependency on the retired backends and was confirmed to pass before this upgrade; it was never attempted. When four of six test files are known or suspected to be blocked by an external dependency, that is a reason to run the other two, not to skip the whole directory.
- **Don't let "the backend is unreachable from here" stand in for "the backend no longer exists."** The session's own diagnosis (no outbound network in this sandbox) was true but materially incomplete, and led it to frame several confirmed-pre-existing failures as sandbox-specific limitations of this verification attempt rather than as facts about the target repository that would hold in any environment.

Against [R18](R18-codex-with-system-monarch-legacy.md) — the only other evaluated run on this exact target, same Node 18/20 Hapi/webpack/Gulp upgrade — this run's change is far smaller: **12 files / 609 LoC against R18's 34 files / 1,378 LoC**, roughly a third the footprint. Some of that gap is real scope difference (R18's plan additionally touched `Makefile`, `.eslintrc`, template/UI files this run left untouched, and repaired a Phenogrid/D3 initializer issue this run never reached), and some of it reflects that this run's `USE_SPA=1` regressions remain unfixed rather than repaired the way R18's equivalent webpack-5/Hapi findings were. A smaller diff is not on its own evidence of a cleaner migration.

Compared with the four existing C-series ablation points, this run sits closer to C1/C3 in task size (a real multi-service, runtime-surfaced application, not C4's two-file toolchain bump) but, like C2 and C4, produced correct work that was never committed. Its BPR, after correcting the attribution of two behaviours that were wrongly scored as upgrade-caused "missing" when they were confirmed pre-existing, and after folding in the `USE_SPA=1` build check as a genuine, unfixed regression, is 0.89 (8/9) — middling against the other four C-series runs, and a reminder that the two corrections pull in opposite directions: the pre-existing-baseline correction raises this run's score by removing blame that was never fair, while actually running the one previously-skipped declared check lowers it by surfacing two real breaks that fixing-on-the-spot would have hidden from the comparison.
