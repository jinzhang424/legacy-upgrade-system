## Run-specific recommendations

- **Commit before reporting a task as "done, verified as far as this sandbox allows."** Eight days of a clean, correct, uncommitted diff is still zero durability; a single `git commit` at the end of the upgrade work would have cost one tool call and removed the risk entirely, the same recommendation C4 made for PeelAndSlice.
- **State "not attempted" and "attempted but failed" in visibly different language, in the first sentence, not only in a detailed table several paragraphs down.** Four of eight declared checks in this run were never run at all; that is a materially different and more serious gap than "ran and found a defect," and the closing summary's structure made the two easy to conflate at a skim.
- **Follow the project's own CLAUDE.md impact-analysis mandate for every touched symbol, not a representative one.** Running `gitnexus_impact` once (on `wrapRouteGet`) and treating that as covering `wrapResponse`, `wrapRoutePost`, `wrappedHandler` and five other touched symbols is a reasonable judgement call under time pressure, but it is not what the project's own stated policy, which the harness surfaces unconditionally, actually requires.
- **Re-run the developer test suite against a reachable backend (or a local mock) before closing out a migration this size.** `tests/*.js` never got past the first network call in this sandbox; that leaves the actual behavioural correctness of the engine's GOLR/SciGraph-dependent methods — the part of the stack the fibers rewrite touched most directly — entirely unverified by anything other than code reading.
- **Treat an evaluation harness's own setup step (here, `gitnexus analyze`) as part of the diff-hygiene surface to report, not as neutral background.** It produced four new untracked paths and a `.gitignore` edit that had nothing to do with the upgrade and were never surfaced to the user.
- **For a target this size, size the five-workflow manual-verification ask against what the environment can actually reach before the session starts.** The brief named five specific browser workflows that all depend on `monarchinitiative.org`; a one-line DNS check at the start of the session would have surfaced the sandbox's lack of outbound network immediately, rather than after most of the upgrade work was already done.

Compared with the four existing C-series ablation points, this run sits closer to C1/C3 in task size (a real multi-service, runtime-surfaced application, not C4's two-file toolchain bump) but, like C2 and C4, produced correct work that was never committed. Its BPR (0.80) is the best of the five C-series runs on raw arithmetic, but on the smallest declared-check completion rate of any of them — 4 of 8 named validation steps, not merely found wanting but never run. The one finding worth carrying forward into the overview alongside C4's "produces correct work and never gives it a commit": a direct Claude Code session that hits a real, severity-defining, out-of-scope blocker mid-task (here, node-fibers) and stops to ask the user rather than guessing is exactly the judgement call the R-series pipeline's fixed four-stage structure has no equivalent mechanism for — but the same session, left to self-report its own completion, undercounts what it didn't finish more easily than it undercounts what it did.
