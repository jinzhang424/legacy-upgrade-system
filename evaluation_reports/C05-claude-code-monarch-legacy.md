## Data loss and recovery (7 Oct 2026)

Asked to test `mng-build`, the agent first ran `git status` as a sanity check and found a **clean working tree** on `claude/upgrade` — no trace of any of the twelve files the original session had edited, and `package.json`/`.babelrc` showing the unmodified pre-upgrade content (`hapi@^16.6.2`, `wait.for@^0.6.6`, Babel 6 `"presets": ["env"]`). The new file `lib/monarch/web/syncHttpWorker.js` the session had created no longer existed on disk at all.

Forensic sequence, run before touching anything further:

1. `git reflog` showed the branch had been checked out away from `claude/upgrade` and back twice since the original session, via two other branches: `codex-raw-upgrade` and `upgrade/node18-20-dependency-upgrade`.
2. `git log` on those two branches showed commits — `upgrade`, `upgrade: node18-20-dependency-upgrade`, `add confidence score` — that are not from this session and use R-series pipeline vocabulary ("confidence score"), indicating a **separate, parallel `$upgrade`-style pipeline run against this same repository**, working in the same shared checkout.
3. `git stash list` showed exactly one stash. Reading its diff (`git stash show -p`) confirmed it belongs to that other run, not this one: it touches files this session never touched (`Makefile`, `templates/search_results.mustache`, `ui/main.js`, `webpack.make.js`) and its `.babelrc` content (`[["@babel/preset-env", {"modules": false}]]`) differs from this session's own (`{ "modules": "commonjs" }`). This session's edits are not in a stash, not on any branch, not anywhere — they were discarded outright by a `git checkout` to one of those other branches sometime after the original session ended.

This is the same failure mode [C04](C04-claude-code-peelandslice.md) documented for PeelAndSlice (an unrelated pipeline run resetting a shared working directory and discarding a Claude Code session's uncommitted edits with no trace) — except there it was discovered after the fact; here the agent caught it in the act, mid-request, before running a single stale-state test and reporting a false result. The agent stopped, explained the finding, and asked the user how to proceed rather than silently testing the reverted original code and calling it "the upgrade."

**Recovery.** On the user's instruction, the agent reconstructed all twelve file edits plus the new `syncHttpWorker.js` from its own memory of the original session's work (not from any surviving artifact — there was none), verified the resulting diff against `e33024b1` matched the original exactly (file-for-file), reinstalled dependencies (`npm install`, 1,814 packages), and regenerated the two build-time-generated bundles (`gen/bbop.min.js`, `gen/phenogrid.min.js`) via `utils/bbop-webpack.config.js` / `utils/phenogrid-webpack.config.js`.

**Testing `mng-build` (`USE_SPA=1 npm run wbs-build`, via the same direct-command workaround as before) immediately surfaced two further, real, previously-undiscovered regressions** — found only because this was the first time in the entire run that the `USE_SPA=1` code path was actually executed rather than left as a declared-but-unattempted check:

- `ui/index.ejs` built its `<link>`/`<script>` tags from `webpackConfig.output.publicPath` and `webpack.assetsByChunkName['app']` — globals that `html-webpack-plugin` injected into its EJS template context in v3, and removed entirely in v4+. The build failed outright: `ReferenceError: webpack is not defined`. Fixed by switching to the v5-supported `htmlWebpackPlugin.files.css`/`.js` arrays, which already include the correct `publicPath`-prefixed URLs.
- Once that was fixed, the build succeeded but rendered `<img src="[object Module]">` for the two inline logo images. `file-loader`/`url-loader`'s newer major versions default to ESM exports (`{ default: url }`); `require('./assets/img/monarch-logo.png')` in the same CommonJS-executed EJS template got the module wrapper object instead of the plain string URL the original webpack 4 toolchain returned. Fixed with `esModule: false` on both loaders, restoring the exact original return shape.

With both fixes applied, `mng-build` compiled cleanly (0 errors, the same pre-existing Bootstrap/Sass deprecation warnings as the non-SPA build) and `dist/index.html` was confirmed to contain a real, correct asset URL (`/dist/f5d8cbce247da9a3650423f72683b56e.png`) rather than the broken placeholder. The work — now including both new fixes — was committed: `115217c6`, 13 files changed. The `USE_SPA=1` **dev-server/proxy** half of the originally-declared check (as opposed to the build half just tested) remains not attempted; see 1.1 and 1.3.

This correction **does not change the strict C/T/FBSR scoring philosophy** — a check that was skipped and then run and fixed is a real, positive change to T, not a retroactive excuse — but it does mean the `USE_SPA=1` build check specifically moves from "0 — never attempted" to "1 — passes, after two real fixes," and the overall declared-check completion count improves from 4 of 8 to 5 of 8 (see 1.1).

## Pre-existing baseline defects (confirmed, not attributable to this upgrade)

A later correction from the user, which this revision incorporates, confirmed the following as pre-existing in the repository *before* this session's upgrade work began — none of them are regressions this upgrade introduced, and several directly change how two of the findings below should be attributed:

- **Build-order defect.** `npm run wbs-build` only ever ran webpack; `conf/golr-conf.json` is generated by the separate Gulp build (`gulp make-golr-conf`). A genuinely clean checkout running `wbs-build` then `start` could fail with `ENOENT` on that file. This structure already existed at base commit `e337d87a`. This session never hit it, because `conf/golr-conf.json` already existed on disk from an earlier build; the session did not generate it freshly and so could not have surfaced this gap either way.
- **Retired backend services.** `conf/server_config_dev.json` points at `scigraph-ontology-dev.monarchinitiative.org`, `scigraph-data-dev.monarchinitiative.org`, `solr-dev.monarchinitiative.org`, and a legacy beta OwlSim endpoint — services that no longer provide the APIs Monarch expects, independent of any sandbox network restriction. This means several of this session's own "could not verify" findings (see 1.1 and 1.3 below) were **never passable by any upgrade**, not merely blocked by this particular environment. The session's own framing — "this sandbox has no outbound network" — was true but incomplete; the more precise cause is that the dev-tier backends themselves are gone.
- **Existing tests already depended on those retired services.** `apitest.js` could not complete its GOLR/SciGraph assertions and `class-info-test.js` failed resolving the SciGraph hostname *before* this upgrade, for the same reason this session's own run of `class-info-test.js` failed. `phenopacket-test.js`, which has no network dependency, remained runnable and passing pre-upgrade — this session never ran it, which is a real gap in its own verification (see "Run-specific recommendations"), independent of the backend question.
- **Windows script incompatibility and the Gulp `mkdir` task** were both pre-existing: many npm/Makefile commands use POSIX-only syntax (inline env vars, `rm`, background `&`, `ln -s`, colon-separated `NODE_PATH`) that does not run through `cmd.exe` directly, and Gulp's temporary-directory task's shell `mkdir` was never portable to Windows either. Both predate this upgrade and are not things the gulp 3→4 migration (or anything else in this session) broke.
- **Missing lint configuration** (`wbs.eslintrc` absent) was pre-existing, as the session itself suspected but could not confirm at the time.
- **Node 18/20 incompatibility was inherent in the old dependency graph** — `node-fibers`/`wait.for`, `node-sass`, the old Hapi, and the old Webpack/Babel/Gulp toolchain all targeted Node 6-era tooling and could not be expected to install cleanly on Node 18/20 without exactly the kind of intervention this session performed.
- **The old dependency graph's security debt, including the Axios 0.18 CVEs this upgrade specifically targeted, was pre-existing** — consistent with what `npm audit` showed in-session.
- **Two items remain baseline-indeterminate, not attributable either way:** the exact behaviour by which an unhandled Axios/`sync-rpc` rejection terminates the whole Node process (observed in this session's `class-info-test.js` run — see 1.2), and analytics-page behaviour (never investigated in this session at all). Neither has a successful pre-upgrade baseline to compare against, so neither is scored below as preserved, missing, or upgrade-caused.

This correction **does not change the strict C/T/FBSR scoring** in 1.1 below — those checks still did not run to a pass, regardless of why — but it does change which failures are fairly attributable to this session's work versus inherited, pre-existing baseline limitations that no upgrade session, in this sandbox or any other, could have cleared. It also reclassifies two cells in the 1.3 behaviour-preservation table from "missing" (implying the upgrade broke something) to "excluded" (the behaviour was already broken and nothing here regressed it).

## What was broken afterwards

1. **The entire original upgrade was discarded with no trace, exactly as the zero-durability risk this report had already flagged predicted.** It was not committed (as this report noted on 3 Oct), and sometime afterward a separate, parallel `$upgrade`-pipeline-style process checked out two other branches in the same shared working directory, silently wiping every uncommitted edit. Nothing survived in a stash, a branch, or anywhere else. This is the same failure mode C4 documented for PeelAndSlice, now confirmed to have actually happened to this run too, not merely to be a risk of it. The work was reconstructed and committed (`115217c6`) on 7 Oct; see "Data loss and recovery."
2. **Five of the eight declared validation steps were never run to a real pass**, not merely failed: `npm run wbs-lint`, the five browser workflows, `make test`/`tests/*.js`, and the `USE_SPA=1` dev-server/proxy half. (The `USE_SPA=1` build half now passes, after two fixes — see item 9.) The original closing summary disclosed the gap, but a reader who only reads its opening line ("the full monarch-app dependency upgrade... is done and verified as far as this sandbox allows") could reasonably come away believing more was confirmed than actually was. Two of the remaining gaps (the browser workflows, the test suite's network-dependent members) were never passable in the first place — the backends are retired — but lint and the SPA dev-server half are plain gaps with no such excuse, and `phenopacket-test.js`, the one test with no network dependency at all, was never run despite being free to attempt.
3. **`wbs.eslintrc` is still missing.** Both `npm run wbs-lint` and the new `eslint-webpack-plugin` reference a file that does not exist anywhere in the repository — confirmed pre-existing, correctly identified by the session as likely pre-existing, but left unresolved.
4. **GitNexus's own project policy was only partly followed.** `detect_changes` itself reports 9 touched symbols; `impact` was run for 1 of them. No HIGH/CRITICAL-risk warning was ever surfaced because `impact` was essentially never asked.
5. **The `gitnexus analyze` step itself left a small, unrequested diff.** Running it (as the project's own CLAUDE.md requires before any edit) created `CLAUDE.md`, `AGENTS.md` and `.claude/skills/` as new untracked files and added one line (`.gitnexus`) to `.gitignore` — none of it part of the requested upgrade, none of it mentioned to the user as a diff-hygiene item, and none of it cleaned up. ## Run-specific recommendations

- **Commit before reporting a task as "done, verified as far as this sandbox allows" — this is no longer a hypothetical.** The uncommitted diff was in fact discarded, with no trace, by an unrelated process sharing the same working directory, exactly as C4 predicted for PeelAndSlice. A single `git commit` at the end of the original upgrade work would have cost one tool call and prevented the loss entirely; it was finally done on the second attempt, after the damage.
- **Run `gitnexus_detect_changes()` immediately before every commit, including a recovery commit made under time pressure.** It was skipped both times a commit (or the moment just before one) occurred in this session, despite the project's own `CLAUDE.md` requiring it unconditionally — the second skip happening with the GitNexus server freshly reconnected and available.
- **When re-applying lost work, treat it as a second chance to run the checks that were skipped the first time, not just a restoration.** That is exactly what happened here by the user's explicit instruction to test `mng-build`, and it is what surfaced two real regressions that had been sitting in the "committed" upgrade undetected. A rote restore-and-recommit, without re-testing, would have shipped them.
- **State "not attempted" and "attempted but failed" in visibly different language, in the first sentence, not only in a detailed table several paragraphs down.** Four of eight declared checks in this run were never run at all; that is a materially different and more serious gap than "ran and found a defect," and the closing summary's structure made the two easy to conflate at a skim.
- **Follow the project's own CLAUDE.md impact-analysis mandate for every touched symbol, not a representative one.** Running `gitnexus_impact` once (on `wrapRouteGet`) and treating that as covering `wrapResponse`, `wrapRoutePost`, `wrappedHandler` and five other touched symbols is a reasonable judgement call under time pressure, but it is not what the project's own stated policy, which the harness surfaces unconditionally, actually requires.
- **Re-run the developer test suite against a reachable backend (or a local mock) before closing out a migration this size.** `tests/*.js` never got past the first network call in this sandbox; that leaves the actual behavioural correctness of the engine's GOLR/SciGraph-dependent methods — the part of the stack the fibers rewrite touched most directly — entirely unverified by anything other than code reading.
- **Treat an evaluation harness's own setup step (here, `gitnexus analyze`) as part of the diff-hygiene surface to report, not as neutral background.** It produced four new untracked paths and a `.gitignore` edit that had nothing to do with the upgrade and were never surfaced to the user.
- **For a target this size, check whether the named backends are even still live before the session starts, not just whether this particular sandbox can reach them.** The brief named five browser workflows and a test suite that all depend on `monarchinitiative.org` dev-tier services; those services are confirmed retired, independent of sandbox network access. A one-line reachability check at the start — ideally against a source of truth that distinguishes "retired" from "temporarily unreachable" — would have let the session say so immediately and precisely, rather than attributing the gap to its own sandbox after most of the upgrade work was already done.
- **Run every test that doesn't need the network, even when most of the suite does.** `phenopacket-test.js` had no dependency on the retired backends and was confirmed to pass before this upgrade; it was never attempted. When four of six test files are known or suspected to be blocked by an external dependency, that is a reason to run the other two, not to skip the whole directory.
- **Don't let "the backend is unreachable from here" stand in for "the backend no longer exists."** The session's own diagnosis (no outbound network in this sandbox) was true but materially incomplete, and led it to frame several confirmed-pre-existing failures as sandbox-specific limitations of this verification attempt rather than as facts about the target repository that would hold in any environment.

Compared with the four existing C-series ablation points, this run sits closer to C1/C3 in task size (a real multi-service, runtime-surfaced application, not C4's two-file toolchain bump), and it is now the **first C-series run whose work is actually committed** — but only after becoming the clearest demonstration yet of why that matters: C4 documented PeelAndSlice's uncommitted work vanishing between sessions as a discovered-after-the-fact finding; this run's uncommitted work vanished in exactly the same way, between the original session and the follow-up, caught only because the user happened to ask for one more test. Its BPR, after correcting the attribution of two behaviours that were wrongly scored as upgrade-caused "missing" when they were confirmed pre-existing, and after adding the `USE_SPA=1` build check that the data-loss incident forced a re-test of, is 1.00 (9/9) — the best of the five C-series runs on raw arithmetic, but on the narrowest denominator of any of them, since every behaviour with real failure risk (the five browser workflows, both halves of the test suite, the lint pass, and the SPA dev-server/proxy half) ends up excluded rather than scored. The declared-check completion rate (5 of 8 named validation steps, up from 4) is still the lowest of any C-series run. The findings worth carrying forward into the overview: a direct Claude Code session that hits a real, severity-defining, out-of-scope blocker mid-task (node-fibers) and stops to ask the user rather than guessing is a judgement call the R-series pipeline's fixed four-stage structure has no equivalent mechanism for; the same session, left to self-report its own completion, undercounts what it didn't finish more easily than it misrepresents what it did; and — the sharpest point this run adds to the corpus — **a declared check that is skipped is not merely "unverified," it is a real, uncaught defect sitting in committed code for as long as nobody runs it**, demonstrated here by two genuine regressions that existed for twelve days before the one skipped check was finally executed.
